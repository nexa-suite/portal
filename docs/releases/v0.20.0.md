# Portal v0.20.0

## Summary

Buyer API source-state recovery and honest payment-history feedback for the existing Buyer contracts.

## Why

The Home composition already queried the API sources independently, but a failed `GET /api/v1/client-accounts/me` could be shown as “no client” when the session did not carry a `clientAccountId`. Receivables payment-history failures were also indistinguishable from a successful empty history.

## Scope

- Preserve successful Home sources when the Client Account lookup fails.
- Show an explicit Client Account unavailable state with retry.
- Keep a real unlinked-account response distinct from a technical API failure.
- Show payment-history failures and retry the same receivable without inventing payment data.
- Keep the released Design Lab v1.0.2 token and component boundary.

## Architecture impact

- No new endpoint, entity, domain state or dependency.
- Existing `BuyerAccountApiPort`, `ReceivablesPaymentFacade` and `PAYMENTS_PORT` contracts remain unchanged.
- Portal continues to own Buyer presentation state only; backend remains authoritative for account, receivable and payment truth.

## Security and tenant impact

- No authorization or tenant predicate changed.
- The UI does not infer a Client Account from a failed API call and does not manufacture fallback business data.
- `COMPANY_OWNER`, `SALES`, `WAREHOUSE` and `LOGISTICS`/Dispatch remain Platform concerns. `BOM` remains deferred because no accepted contract exists.
